# P4-01：首批性能优化

日期：2026-11-08。状态：查询优化与第二批内存优化完成，500 MiB 预算与完整 P4-01 验收待继续。

## 本批范围

用户要求优先性能，减少无关验证。先用现有十万提交 / 千条引用参考仓库定位高成本操作，选择有证据的热点修复；不同时引入工作区状态、文件页面或新的存储框架。P4-01 的异常恢复和完整发布性能验收仍单独保留，不因完成一批优化就勾选整项。

## 测量和实施顺序

1. 从当前源码生成 release 工程资源，使用独立应用数据目录，不干扰用户正在使用的应用；记录构建哈希、HEAD、环境与缓存条件。
2. 等元数据索引完整后采样整个 Electron 进程树，区分 main、renderer、GPU、utility、Rust 和 Git。空闲 RSS 求和可能重复计入共享页，短时 CPU 不能代替一分钟发布指标。
3. 串行测量消息命中 / 无命中、OID、活动统计、日期定位及包含分支，记录真实 IPC 响应时间、结果标识和错误；本轮不将响应时间当作绘制时间，也不以少量样本声称 p95 达标。
4. 根据进程分解与代码分析确定最小修正。前后使用同一仓库、窗口和完整索引条件；校对命中数、结果 OID 与取消行为。已有旧基线和输出文件不覆盖。

## 分工与约束

- 核心代理定位 Rust 的扫描、分配、锁与 Git 子进程开销；桌面代理定位协议和 renderer 的重复工作。先只读分析，确认测量后再按文件分配实现。
- 验证代理提供聚焦测量脚本；主代理负责执行测量、确定代码方案、集成与记录。
- 测量期间不并行构建或运行测试。只跑受影响的正确性用例；有性能收益和数据一致性证据后停止扩展验证。
- 保留固定快照、只读仓库、可取消请求与有界 renderer 的约束。不以禁用隔离、隐瞒未完成覆盖或强制 GC 美化常态内存。

## 已发现与实际结果

首次建索引后的诊断发现：十万提交 OID 前缀仅命中一条仍耗时约 254 ms，消息命中 / 无命中约 257 / 211 ms，日期定位约 596–1446 ms。全进程树空闲约 631 MiB，Rust 仅约 18 MiB。首次建索引与 warm 重启不直接比较；正式 before / after 使用同一个完整索引 profile 重启。

本批代码修正：

1. `crates/daemon/src/search.rs`：非空 OID 前缀通过现有 `(snapshot_key, oid)` 索引范围筛选；保留快照水位、其余筛选、精确计数及排序语义。行匹配仅在有身份筛选时读取身份字段、仅读取选中的时间字段；ASCII 消息采用 ASCII 大小写转换，非 ASCII 保留 Unicode case folding。覆盖前缀碰撞、部分水位、组合筛选和 Unicode 情况。
2. `crates/daemon/src/history.rs`：日期拓扑遍历同时保存命中 OID 与序号，内部定位复用该页偏移，免去第二次按 OID 遍历。继续使用原图布局检查点、快照校验与取消处理；覆盖时间逆序和同时间提交的选择规则。
3. 主进程内存仍需根据 warm 的进程分解判断；不将上述 Rust 查询优化宣称为 Electron 常驻内存达标。

正式 warm 前后结果：OID 搜索三次中位数 178.6 → 1.3 ms，消息命中 233.4 → 181.0 ms，无命中 197.1 → 149.9 ms；两处未缓存日期页首次定位 1298.9 → 916.6 ms、1254.7 → 890.5 ms。24 对查询的数据摘要一致，搜索 9 项 / 历史 11 项单测和 4 项受影响集成检查通过，release 构建成功。

整树空闲 RSS 仍约 603 MiB，未达到 500 MiB 目标；不将查询前的内存波动归因于本批修正。首批暂未修改主进程 Ajv 生成链路：一次独立 Node 诊断中三份 schema 编译约 87.5 ms、临时增加约 22 MiB RSS，无法解释或解决整树常驻占用。其后继续定位 Electron / Git 常驻成本，见第二批记录；完整记录、测量边界与复现方式见[首批性能报告](../benchmarks/p4-01-interactive-performance.md)。

## 第二批：常驻内存（已完成本批）

首批已提交为 `670a5e3`。用户要求继续优化内存。本次独立窗口诊断确认 main / renderer 的 JS 活跃堆约 12 / 17 MiB，vmmap 物理 footprint 约 67 / 115 MiB，RSS 包含较多共享代码映射。诊断只用于定位，继续沿用整进程树 RSS 预算，不改统计口径来宣称达标。

优先验证两项可独立回退的小改动：

1. `git_command.rs` / `history.rs`：用有严格字节上界的块预读代替历史流逐行的极小队列。参考仓库约 8 MiB 的拓扑能被紧凑缓冲，让约 36 MiB 的 Git 进程自然退出；更大历史仍受背压限制。保持逐行解析、快照、错误、取消和图检查点语义，不在翻页时反复重启全量拓扑遍历，也不增加磁盘缓存框架。
2. `scripts/protocol-lib.mjs` / main 的生成校验器 / `protocol-transport.ts`：将 Ajv schema 编译移到构建期，运行时保留相同完整校验和错误格式。该项从上一批的暂缓改为实测候选，只在实际 RSS / footprint 有收益时保留；不能把 Node 编译峰值当作 Electron 常驻收益。

代理分别负责 Git 流与主进程校验器，主代理负责测量与记录。只跑流的正确性 / 取消及协议受影响检查；复用同一十万提交完整索引、窗口和独立 profile，测量期间不并行构建。比较查询数据与耗时，避免以显著增加翻页延迟换取更低静态内存。

实测整树空闲 RSS 中位数 603.0 → 566.3 MiB，查询阶段采样峰值 689.7 → 623.4 MiB。Rust 新增约 8.1 MiB 已计入，Git 空闲中位数降为零，main 下降约 9.6 MiB。前后 24 对查询事实一致，受影响检查与 release 构建通过，保留两项修改。大于预读上限的历史仍背压，不以本仓库结果保证所有仓库释放 Git；500 MiB 目标仍未达成。详见[内存实测报告](../benchmarks/p4-01-memory.md)。
