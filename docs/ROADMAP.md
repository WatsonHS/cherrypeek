## 三个可交付节点

1. **M1 结束：历史与搜索预览。** 能浏览历史，使用消息与身份 / 日期 / hash 等筛选；图、diff、路径搜索、统计和自动更新通知尚未齐全。
2. **M3 结束：只读 MVP。** 产品主路径完整，供本机日常尝试；性能结果仍需对照预算，不能称稳定发布。
3. **M4 结束：日用候选版本。** 真实试用和目标平台验证通过，记录已知限制与实测数据。

## 实施顺序的理由

2026-11-08 确认的后续顺序是 P4-09 → P4-10：先补齐“还有什么正在修改、尚未提交”，再完善“单个文件如何演变”。两项均保持只读，可先进入本机试用；M4 原有性能、恢复与发行关卡继续保留。切分支、fetch、stash 的执行方式不作为前置条件，也未排入开发任务。本次只更新规划，不启动实现。

先打通真实 Git 数据与 Electron / Rust 通信，才能测首屏与进程成本。按 2026-11-07 用户确认的顺序，历史分页稳定后先交付元数据索引和搜索，用真实仓库尽早验证查找提交的核心价值，不以完整图布局和 diff 为前置条件。随后补齐图与详情，接入搜索定位和返回；路径历史、统计继续复用同一范围、筛选和时间语义。固定快照与手动刷新在 M1 建立，M3 增加外部变化通知。最后处理打包、平台差异与长期运行。

M0 的 gix 比较是局部、限范围的验证。若 CLI 已满足目标或 gix 存在兼容缺口，保留 CLI 推进 M1；记录结论即可，不阻塞产品。所有后续优化都保持查询接口与结果语义一致。

2026-11-09 用户要求放宽内存目标：本轮采用空闲整树 RSS 800 MiB、交互阶段 1 GiB 观察目标，详见 [VALIDATION](VALIDATION.md)。停止以旧的 500 MiB 作为功能开发阻塞项，当前定向优化收尾后继续 P4-09；长期稳定性和发布验收保留。

## 后续线路：审阅收口与三栏轻量合并（2026-11-17 用户确认方向，待排期）

### 工作流定位与分工原则

面向“不打开传统 IDE / 编辑器、主要对着 Agent 终端进行 Vibe Coding，以 CherryPeek 作为查看仓库状态与把关收口的唯一图形界面”的使用场景。整体确立如下主次分工：

- **首选交给 Agent**：写代码、修改历史（多步或交互式 `rebase`、`reset`、`cherry-pick`、`revert`、`stash`）、排障及结构性或复杂冲突处理，继续以“交给 Agent”作为首选路径。
- **App 内完成审阅收口与顺手小冲突**：看状态、Commit 前审阅把关、确定性收口（Commit / 快进合入主线 / Push / 清理已合入分支），以及推拉 / 合入分叉时顺手可点的少量普通文本冲突，在 App 内保留直接入口或次选路径，减少来回切终端与复制 prompt 的打断。是否值得手动处理由用户判断，App 不自动替用户做取舍。

### 第一阶段（M7）：审阅收口与推送（无冲突单步闭环）

延续 M5“一步完成、不进入冲突中间态、做不到时保持仓库原样并提示交给 Agent”的安全边界：

1. **非强制 Push 与分支清理**：展示本地领先远端的 `↑N` 个待推送提交，支持常规 `push` 与新分支首次推送自动设置上游（`--set-upstream`），严禁 `--force`；远端领先导致被拒时不改动本地，提示先更新或交给 Agent。范围菜单支持一步删除已合入且未被任何 worktree 检出的本地分支（`git branch -d`）。
2. **本地分支快进合入目标分支（如 `feat` → `main`）**：合入前展示将带入的提交列表与改动文件数；目标分支是源分支祖先时一步完成 fast-forward（当前未检出目标分支且目标未被其他 worktree 检出时可直接快进引用，或由用户显式切换后快进）；两侧已分叉不能 fast-forward 时保持仓库原样，首选提示“交给 Agent”（后续可衔接 M8）。
3. **「工作区」页 Commit 前审阅闭环**：
   - **首选交给 Agent**：补齐针对未提交改动的“交给 Agent”入口，在审阅工作区 diff 时可直接选中文件并附修改意见生成 prompt 打回给 Agent，或由 Agent 整理提交。
   - **次选轻量手动提交**：支持文件级暂存 / 取消暂存、确认后丢弃单文件改动，以及同屏审阅编辑 Commit Message（支持读取 `COMMIT_EDITMSG` 等现有草稿）并直接 Commit。触发 `pre-commit` hook 失败时保留暂存区和已写消息，展示原始输出并提供“交给 Agent 修复”。

### 第二阶段（M8）：分叉同步与 JetBrains 式三栏轻量合并（零中间态次选）

替代 2026-11-14 旧版手动合并顺序，聚焦“已提交分支在 Push / 更新 / 合入主线时遇到分叉或一两行小冲突、想顺手点掉直接推走”的场景：

1. **零中间态只读预演**：两侧均为已落盘提交且工作区干净时，先在内存或应用临时目录基于共同祖先与两侧提交计算三方差异，**预览与点选全程不修改 `HEAD`、index 或工作区文件**。
   - 分叉但无冲突时支持一键同步（生成合并提交；若本地仅领先 1 个普通提交，也可选择直接变基以保持线性历史）并继续推送。
   - 存在普通文本冲突时列出冲突文件与块数，“交给 Agent”仍为主按钮，旁设次按钮“顺手解决…”。
2. **JetBrains 式左-中-右三栏双边箭头合并视图**（明确不做 VS Code 式源码内联冲突按钮或“上左右、下结果”的上下分栏勾选）：
   - 打开合并视图时临时收起左侧列表，全宽并排展示 **左栏（本地改动，只读）｜ 中栏（最终合并结果）｜ 右栏（远端 / 待合入改动，只读）**；三栏同步滚动，跨栏使用彩色连接带对齐同一变更块。
   - 左-中与中-右装订线分别提供 **`»` / `«`（将该侧改动块推入中间栏）** 与 **`×`（忽略该侧改动块）**；两侧均需保留时按点击先后顺序自然拼入中间栏，支持单块撤回重置。
   - 无冲突改动默认自动合入中间栏，打开直达第 1 处真冲突，支持上下跳转及在中间栏直接微调局部文本。
   - 顶部实时显示剩余冲突数，清零后确认按钮才可点击，点击确认时一次性写入提交并更新分支；中途按 `Esc` 关闭或点右上角“交给 Agent”直接退出，无需回滚、不留半合并中间态。
3. **明确不进手动合并器的边界（只走“交给 Agent”）**：
   - 本地领先多个提交且要求逐步 `rebase`（可能连续多次冲突的多步状态机）；
   - 文件重命名 / 删改冲突、文件与目录类型冲突、二进制或子模块冲突、多共同祖先（criss-cross）；
   - 工作区存在未提交的已跟踪脏改动。

## 暂不排期

原 2026-11-14 候选中的“已跟踪文件的未提交改动挡住更新时的按块保留 / 合并”和“接手已在进行中的合并或 rebase”移入暂不排期，继续交给 Agent 或终端处理；仅在未来真实使用中确认确有高频需求时再单独评估。

交互式 `rebase -i`、`reset`、`stash`、`cherry-pick`、`revert`、`force push` 继续交给 Agent 或终端，不入排期。重命名分支、打标签保留为低优先级候选，待 M7 / M8 试用后决定。

PR review、账号与云同步、AI 总结、按代码增删内容搜索、跨重命名历史、多 worktree 聚合视图，以及 Linux 与正式分发渠道待目标平台和实际需求明确后单独评估排期。
